# Переезд в Yandex Cloud: три сайта, закрытый репозиторий, процесс изменений

> Ответ на указание владельца 26.11: «Я создал аккаунт в Yandex Cloud. Хочу туда перенести всё, сделать 2 сайта и закрыть репозиторий. Подскажи, как потом действовать при изменениях».
> **Коротко:** сайты dvorami.ru, sledami.ru и zalami.ru (отдельный бренд, A-77, 28.11) будут лежать в хранилище Yandex Cloud, адреса — ваши домены с HTTPS. GitHub остаётся местом, где команда пишет и хранит код (репозиторий станет закрытым), но **перестаёт быть стендом**: стенд — отдельный скрытый бакет в Yandex Cloud. Боты переезжают в облачные функции, иначе в закрытом репозитории не хватит бесплатных минут. Ваша работа — около часа в консоли по списку из раздела 6; всё остальное делаем мы. Цена — **около 50–200 ₽ в месяц** при нашей посещаемости.
> Цены и лимиты помечены 🔶: найдены поиском 27.11.2026, страницы тарифов мы не открываем (правило проекта). Перед включением сверьте по ссылке — порядок величин команда знает и за него отвечает.

## 1. Как всё будет устроено

| Что | Где сейчас | Где будет |
|---|---|---|
| Сайт dvorami.ru | GitHub Pages | бакет `dvorami.ru` в Object Storage |
| Витрина sledami.ru | папка `site/sledami/` на стенде | бакет `sledami.ru` |
| Сайт zalami.ru (A-77: отдельный бренд) | ещё нет; будет папка `site/zalami/` | бакет `zalami.ru` |
| Адреса с www | — | пустые бакеты `www.<домен>` с переадресацией на домен без www (шаг 6.4) |
| Плеер квеста | `site/play/` | во всех бакетах сайтов, один и тот же код |
| Стенд (для проверки) | jastiss.github.io/dvorami | бакет с секретным именем, закрыт от поиска |
| HTTPS на своём домене | — | бесплатный сертификат Let's Encrypt в Certificate Manager |
| DNS доменов | reg.ru | dvorami.ru, sledami.ru, zalami.ru — Cloud DNS (у reg.ru меняются только адреса DNS-серверов); дворами.рф, следами.рф, залами.рф — остаются в reg.ru с переадресацией |
| Боты Telegram | GitHub Actions, круглосуточно | облачные функции (просыпаются на сообщение) |
| Оценки с сайта (A-58), позже оплата (A-17) | — | облачная функция за API Gateway |
| Код, сценарии, ответы | открытый репозиторий | закрытый репозиторий |
| Секреты | GitHub Secrets | GitHub Secrets (для сборки) и Lockbox (для функций) |

**Пять слов из консоли:**
- **Бакет** — папка в облачном хранилище, которая умеет быть сайтом.
- **Сервисный аккаунт** — «робот-пользователь» с узкими правами. Наш робот умеет только класть файлы в четыре бакета (три сайта и стенд).
- **Облачная функция** — маленькая программа, которая спит и просыпается на запрос. Платите за секунды работы.
- **API Gateway** — «входная дверь» для функций: даёт им адрес в интернете.
- **Lockbox** — сейф для паролей и токенов, из которого их читают функции.

**Почему без CDN.** Бакет сам отдаёт сайт по HTTPS на своём домене с сертификатом из Certificate Manager ([инструкция Yandex Cloud](https://yandex.cloud/ru/docs/storage/operations/hosting/own-domain)). CDN нужен при большом трафике или видео — подключим, если понадобится; сайт от этого не меняется ([CDN-хостинг](https://yandex.cloud/ru/docs/cdn/tutorials/cdn-hosting/console)).

**Почему нужен Cloud DNS.** Адрес «без www» (dvorami.ru) нельзя направить на бакет обычной записью CNAME. В Cloud DNS для этого есть запись ANAME — поэтому домены «переезжают» в Cloud DNS, а у reg.ru вы меняете только два адреса DNS-серверов. Домены остаются вашими и продлеваются в reg.ru как раньше. Переадресация дворами.рф (A-55), следами.рф и залами.рф остаётся в reg.ru.

## 2. Что будет закрыто и как

- **Сценарии и ответы (A-48).** После закрытия репозитория `quests/*/quest.json` никто снаружи не видит. На сайт, как и сейчас, попадает только зашифрованное дело `quest.locked.json`; открывает его код доступа ([docs/codes.md](https://github.com/jastiss/dvorami/blob/main/docs/codes.md)). Шифрует сборка в GitHub Actions мастер-кодом из секрета `QUEST_MASTER_CODE` — тут ничего не меняется.
- **Стенд.** Бакет нельзя закрыть паролем, поэтому стенд прячем иначе: секретное имя бакета (его знают только вы и команда), `noindex` и `robots.txt Disallow` на каждой странице, дела — под кодом. Найти его случайно нельзя, проиндексировать — тоже. Если понадобится пароль, его можно поставить «входной дверью» API Gateway — это отдельная работа, пока не рекомендуем.
- **Журналы сборки** в закрытом репозитории тоже закрыты.

## 3. Боты и минуты GitHub — посчитали

У закрытого репозитория на бесплатном тарифе — **2000 минут GitHub Actions в месяц** 🔶 ([тарифы GitHub](https://docs.github.com/en/billing/managing-billing-for-github-actions/about-billing-for-github-actions)). У открытого — без ограничений, поэтому сейчас мы о минутах не думали.

| Что крутится сейчас | Как часто | Минут в месяц |
|---|---|---|
| Игровой бот @dvorami_bot (`feedback-bot.yml`) | круглосуточно, задание по ~5,5 ч | **~43 000** |
| Входящие от вас (`telegram-inbox.yml`) | 33 раза в день | ~1000 |
| Посты в канал (`channel-post.yml`) | раз в час | ~720 |
| Сборка стенда (`pages.yml`) | ~5 пушей в день × ~7 мин | ~1000 |
| Бот-ведущий квеста (`quest-play.yml`) | по запуску, 5 ч | ~300 за запуск |
| Отчёты в Telegram и прочее | | ~100 |
| **Итого** | | **~46 000 — в 23 раза больше лимита** |

Даже без игрового бота выходит ~3000 минут. Поэтому **в закрытом репозитории боты в Actions не остаются**.

**Выход: боты — облачные функции с вебхуком.** Сейчас бот каждые несколько секунд спрашивает Telegram «есть новое?» (long polling) — и для этого всё время работает машина GitHub. С вебхуком наоборот: Telegram сам вызывает функцию, когда пришло сообщение. Функция работает доли секунды. Бесплатный объём функций — 1 млн вызовов и 10 ГБ×ч в месяц 🔶 ([free tier Yandex Cloud](https://yandex.cloud/ru/docs/billing/concepts/serverless-free-tier)); нам нужно несколько тысяч вызовов.

| Бот | Куда | Как |
|---|---|---|
| Входящие от вас | функция + вебхук | пишет ваши указания в `DIRECTIVES.md` закрытого репозитория через GitHub API (токен с правом только на этот репозиторий — в Lockbox) |
| Игровой бот и оценки (A-58) | функция + вебхук | очередь модерации и одобренные оценки — в закрытом бакете; кнопки «✅ В рейтинг» остаются |
| Посты в канал | функция + таймер раз в час | расписание — как сейчас |
| Бот-ведущий квеста | функция + вебхук | последним: основной путь — веб-плеер |
| Отчёты команды владельцу | остаются в Actions | ~60 минут в месяц |

**Защита вебхуков.** Адрес функции открыт в интернет, поэтому каждая функция (1) принимает вызов, только если в нём есть секретный заголовок, который Telegram присылает по нашей настройке вебхука (`secret_token`), и (2) как сейчас, слушает команды только из своего чата. Токен GitHub для входящих — с правом только на запись в этот репозиторий и со сроком действия; у функций — свой сервисный аккаунт с правом читать только свой секрет Lockbox.

**Что остаётся в GitHub Actions:** сборка и деплой сайтов и отчёты. Чтобы уложиться в 2000 минут: браузерный автотест плеера на стенде — только когда менялись плеер или дела (команда всё равно гоняет его до пуша), кэш браузера, новый пуш отменяет недоделанную сборку. Оценка: **~600–1200 минут в месяц**, запас есть. Не хватит — GitHub Pro (~4 $/мес, 3000 минут) 🔶.

## 5. Процесс изменений — как будем работать после переезда

```
feature/… ──► main ──► стенд (секретный адрес)
                  └─ «да» владельца ──► production ──► dvorami.ru, sledami.ru, zalami.ru
```

| Шаг | Кто | Что происходит |
|---|---|---|
| 1. Работа | команда | правки в ветке `feature/…`; автотесты локально |
| 2. Предпросмотр (по желанию) | команда | ветку можно выложить на стенд в папку `_preview/<имя>/`, не трогая основной стенд |
| 3. Слияние в `main` | Продюсер, после рецензента | сборка: автотест плеера, шифрование дел, проверка «нет открытого текста» → **стенд обновляется сам** за 2–4 минуты. Красный тест — стенд остаётся прежним |
| 4. Вопрос вам | Продюсер | в APPROVALS: «выложить на боевой: что изменилось, ссылка на стенд» + готовый запрос на слияние (pull request) `main → production` |
| 5. Ваше «да» | **вы** | открываете запрос на слияние → зелёная кнопка **Merge**. Только вы. Это и есть «да» |
| 6. Боевой деплой | автоматически | та же сборка + выкладка в бакеты `dvorami.ru`, `sledami.ru` и `zalami.ru` (когда появится `site/zalami/`) за 3–5 минут |

**Почему сливаете вы, а не мы.** На бесплатном тарифе в закрытом репозитории нельзя технически запретить пуш в ветку и поставить «одобрение перед деплоем» 🔶. Поэтому правило простое: команда в `production` не пушит никогда; кнопку Merge нажимаете вы. Хотите проще — напишите «A-N да» в Telegram, и Продюсер сольёт сам, сославшись на ваш ответ.

**Откат.** Что-то сломалось на боевом:
1. Быстро (1 минута): GitHub → Actions → «Сайт — деплой в Yandex Cloud» → последний **зелёный** запуск ветки `production` → **Re-run all jobs**. Он выложит ту версию заново.
2. Аккуратно: команда делает «откатывающий» коммит (`git revert`) в `production` — деплой проходит сам.
3. На крайний случай: в бакетах включено хранение версий файлов — любой файл можно вернуть в консоли.

**Что видит игрок при обновлении.** Плеер работает без сети и держит дело в памяти телефона. После выкладки он подхватит новую версию при следующем открытии с интернетом. Если изменилась версия дела, игрок в середине прохождения увидит экран «Вышла новая версия дела: начать заново / продолжить» (сделано 27.11, T-105).

**Черновик сборки** — [docs/deploy-yc.workflow.yml](https://github.com/jastiss/dvorami/blob/main/docs/deploy-yc.workflow.yml). Лежит в `docs/`, потому что в `.github/workflows/` команде писать нельзя (автопроверка). Вы перенесёте его одним действием в шаге 7. Старый `pages.yml` работает, пока репозиторий открыт, и мы отключим его после переезда.

## 6. Что сделать вам — по шагам

Консоль: https://console.yandex.cloud. Порядок важен: сайты не перестанут работать ни на минуту (раздел 7).

**Шаг 1. Платёжный аккаунт и бюджет (5 мин).** «Биллинг» → убедитесь, что аккаунт «Активен» и привязана карта. Там же → «Бюджеты» → «Создать»: тип «Расходы», сумма `500`, уведомление на 50% и 100% на вашу почту.

**Шаг 2. Каталог (1 мин).** Главная консоли → облако → «Создать каталог» → имя `dvorami` → «Создать». Дальше всё — внутри этого каталога.

**Шаг 3. Бакеты (10 мин).** «Object Storage» → «Создать бакет», четырежды (сделано 28.11):

| Имя | Доступ на чтение объектов | Доступ к списку объектов | Класс |
|---|---|---|---|
| `dvorami.ru` | Публичный | Ограниченный | Стандартное |
| `sledami.ru` | Публичный | Ограниченный | Стандартное |
| `zalami.ru` | Публичный | Ограниченный | Стандартное |
| `dvorami-stand-` + 6 случайных букв и цифр | Публичный | Ограниченный | Стандартное |

Максимальный размер — `1 ГБ`. В каждом бакете: «Веб-сайт» → «Хостинг» → главная страница `index.html`, страница ошибки — пусто → «Сохранить». В бакетах `dvorami.ru`, `sledami.ru` и `zalami.ru` ещё: «Версионирование» → «Включить» (это наш откат).
Прислать команде: имя бакета стенда — личным сообщением или в Telegram-бот (это не пароль, но в отчёты его не пишем).

**Шаг 4. Робот для выкладки (5 мин).** «Identity and Access Management» → «Сервисные аккаунты» → «Создать» → имя `dvorami-deploy`, **роли не добавлять**. Затем в каждом из четырёх бакетов (`dvorami.ru`, `sledami.ru`, `zalami.ru`, стенд): «Права доступа» → «Назначить роли» → `dvorami-deploy` → роль `storage.editor`. Так робот может менять только эти четыре бакета и ничего больше. Бакетам `www.…` из шага 6.4 роль не нужна.
Потом в аккаунте `dvorami-deploy` → «Создать новый ключ» → «Создать статический ключ доступа». Покажутся два значения — **никуда их не пересылайте**, сразу шаг 5.

**Шаг 5. Ключ — в секреты GitHub (3 мин).** https://github.com/jastiss/dvorami/settings/secrets/actions → **New repository secret**, трижды:
- Name `YC_SA_KEY_ID` → Secret: «Идентификатор ключа»;
- Name `YC_SA_SECRET` → Secret: «Ваш секретный ключ»;
- Name `YC_STAND_BUCKET` → Secret: имя бакета стенда (секретом — тогда GitHub скрывает его в журналах сборки, пока репозиторий ещё открыт).

Там же вкладка **Variables** → **New repository variable**, трижды: `YC_PROD_BUCKET` = `dvorami.ru`; `YC_SLEDAMI_BUCKET` = `sledami.ru`; `YC_ZALAMI_BUCKET` = `zalami.ru` (заведено 28.11; сборка прочтёт его и как Variable, и как Secret).
Прислать команде: «ключ заведён». Мы выложим стенд и пришлём ссылку вида `https://dvorami-stand-….website.yandexcloud.net/` — проверьте с телефона.

**Шаг 6. DNS — домены ведут на бакеты (40 мин + ожидание до суток).** Зоны `dvorami.ru.`, `sledami.ru.`, `zalami.ru.` созданы (28.11). Короткое сообщение «что сделать сейчас» — [docs/yandex-cloud-step6.md](https://github.com/jastiss/dvorami/blob/main/docs/yandex-cloud-step6.md).

Простыми словами: DNS — «телефонная книга» домена: по имени `dvorami.ru` браузер узнаёт, куда идти. Сейчас книгу ведёт reg.ru. Вы завели такие же книги в Yandex Cloud (это и есть зоны) — теперь (1) вписываете в них строки-записи, (2) говорите reg.ru «книгу теперь ведёт Яндекс» (смена DNS-серверов, п. 6.6). До п. 6.6 reg.ru остаётся главным, и ничего не ломается: записи в Cloud DNS просто ждут.

**6.1. Посмотреть, что записано в reg.ru сейчас (5 мин).** reg.ru → вход → «Домены» → нажмите на `dvorami.ru` → «DNS-серверы и управление зоной» (в части кабинетов — вкладка «Управление» → «Управление зоной»). Ниже адресов DNS-серверов — список «Ресурсные записи». То же для `sledami.ru` и `zalami.ru`. Что из списка переносить:

| Что видите в reg.ru | Переносить в Cloud DNS? |
|---|---|
| NS, SOA | **нет** — в зоне Yandex Cloud свои, они уже есть |
| A и AAAA для `@` или `www`, CNAME `www` (заглушка reg.ru; или `185.199.10x.153` и `jastiss.github.io` — если подключали GitHub по старой инструкции) | **нет** — вместо них записи сайта из п. 6.3 |
| MX (почта) | **да**, каждую |
| TXT: `v=spf1…`, `yandex-verification…`, `google-site-verification…`, запись с именем `mail._domainkey` (подпись почты) | **да**, каждую |
| Что-то ещё (CNAME `mail`, `autoconfig`, SRV…) | **да**, как есть; сомневаетесь — скриншот списка в бот, ответим |

Если в списке только NS, SOA и A/CNAME — переносить нечего (так бывает, когда почты на домене нет), сразу п. 6.2.

**6.2. Как создать запись в Cloud DNS.** Консоль → каталог `dvorami` → «Cloud DNS» → нажмите на зону (например, `dvorami.ru.`) → «Создать запись». Поля:
- «Имя» — часть до домена: для самого домена оставьте **пустым** (не даёт — `@`), для www — `www`, для подписи почты — `mail._domainkey`;
- «Тип» — из таблицы;
- «TTL» — `600` (это 10 минут: столько интернет помнит старое значение после правки);
- «Значение» — копируйте как есть. Попросит точку в конце (`…yandexcloud.net.`) — добавьте.

**6.3. Записи сайта — по две в каждой зоне (5 мин).**

| Зона | Имя | Тип | TTL | Значение |
|---|---|---|---|---|
| `dvorami.ru.` | пусто | ANAME | 600 | `dvorami.ru.website.yandexcloud.net` |
| `dvorami.ru.` | `www` | CNAME | 600 | `www.dvorami.ru.website.yandexcloud.net` |
| `sledami.ru.` | пусто | ANAME | 600 | `sledami.ru.website.yandexcloud.net` |
| `sledami.ru.` | `www` | CNAME | 600 | `www.sledami.ru.website.yandexcloud.net` |
| `zalami.ru.` | пусто | ANAME | 600 | `zalami.ru.website.yandexcloud.net` |
| `zalami.ru.` | `www` | CNAME | 600 | `www.zalami.ru.website.yandexcloud.net` |

ANAME — запись Cloud DNS для «голого» домена: работает как CNAME (направляет имя на адрес бакета-сайта), но разрешена в корне зоны рядом с почтой. Сайт на своём домене Yandex Cloud отдаёт, только если **имя бакета совпадает с доменом** — у вас так и есть (`dvorami.ru`, `sledami.ru`, `zalami.ru`).

**6.4. Бакеты для www (5 мин).** Адрес `www.dvorami.ru` обслуживает только бакет с именем `www.dvorami.ru` — он пустой и просто перекидывает на основной адрес. «Object Storage» → «Создать бакет», трижды: `www.dvorami.ru`, `www.sledami.ru`, `www.zalami.ru`; доступ как в шаге 3, размер 1 ГБ. В каждом: «Веб-сайт» → «Переадресация» → домен `dvorami.ru` (соответственно `sledami.ru`, `zalami.ru`), протокол `HTTPS` → «Сохранить». Роли роботу и версионирование не нужны — файлов там не будет.

**6.5. Перенесённые записи из п. 6.1** — в ту же зону, с тем же именем и типом. MX в Cloud DNS пишется одной строкой «приоритет, пробел, сервер с точкой», например `10 mx.yandex.net.`; TXT — текст целиком, как в reg.ru.

**6.6. Сменить DNS-серверы в reg.ru — когда для этого домена сделаны 6.3–6.5 (3 мин).** reg.ru → «Домены» → `dvorami.ru` → «DNS-серверы и управление зоной» → «Изменить» → «Свой список DNS-серверов» → первая строка `ns1.yandexcloud.net`, вторая `ns2.yandexcloud.net` (IP-адреса не нужны) → «Готово». Повторите для `sledami.ru` и `zalami.ru`. Переключение — от 15 минут до суток.
- **Кириллические дворами.рф, следами.рф, залами.рф не трогайте** — они остаются на DNS-серверах reg.ru ради переадресации (п. 6.7).
- Если подключали dvorami.ru к GitHub Pages по старой инструкции: https://github.com/jastiss/dvorami/settings/pages → «Custom domain» → **Remove**. Иначе старый стенд начнёт перекидывать на новый, пока ещё пустой сайт.

**6.7. Переадресация .рф (reg.ru, 5 мин на домен; можно позже).** Как в шаге 1 [docs/domains-new.md](https://github.com/jastiss/dvorami/blob/main/docs/domains-new.md): «Переадресация», постоянная 301, с сохранением пути, без маскировки — дворами.рф → `https://dvorami.ru`, следами.рф → `https://sledami.ru`, залами.рф → `https://zalami.ru`. Если услуга платная — не подключайте, напишите нам: тогда .рф тоже переедут в Cloud DNS, а переадресацию сделает пустой бакет, как для www.

**6.8. Проверка (через 1–24 часа).**
1. https://dnschecker.org/#NS/dvorami.ru — в большинстве строк `ns1.yandexcloud.net` и `ns2.yandexcloud.net`. То же для `sledami.ru` и `zalami.ru`.
2. Откройте `http://dvorami.ru` (именно http, без s). Страница с ошибкой Yandex («NoSuchKey», 404 или «AccessDenied») — **правильно**: адрес уже ведёт в бакет, бакет пока пуст, сайт выложим после шага 7. Если открылась страница reg.ru — DNS ещё не переключился, подождите.
3. `https://…` пока ругается на сертификат — это шаг 7.
4. Напишите в бот: «DNS переключён» (и было ли что переносить из п. 6.1).

Не так что-то с почтой — верните в п. 6.6 DNS-серверы reg.ru (`ns1.reg.ru`, `ns2.reg.ru`): всё откатится за час-сутки.

🔶 Устройство записей (ANAME для домена, CNAME для www, имя бакета = домен, бакет-переадресация для второго адреса) — по документации Yandex Cloud: [свой домен для бакета](https://yandex.cloud/ru/docs/storage/operations/hosting/own-domain), [несколько доменов у сайта](https://yandex.cloud/ru/docs/storage/operations/hosting/multiple-domains/console), [статический сайт — пример целиком](https://yandex.cloud/ru/docs/tutorials/web/static/console), [типы записей Cloud DNS](https://yandex.cloud/ru/docs/dns/concepts/resource-record). Страницы найдены поиском 28.11, не открывались (правило проекта); названия пунктов меню reg.ru — по нашей прежней инструкции, интерфейс мог измениться: не нашли пункт — скриншот в бот.

**Шаг 7. Сертификаты и сборка (15 мин) — после «DNS переключён».** «Certificate Manager» → «Добавить сертификат» → «Сертификат от Let's Encrypt» → имя `dvorami`, домены `dvorami.ru` и `www.dvorami.ru` (оба в одном сертификате), тип проверки — DNS → «Создать запись» (консоль добавит её в зону сама). То же — сертификат `sledami` (`sledami.ru`, `www.sledami.ru`) и `zalami` (`zalami.ru`, `www.zalami.ru`). Через 5–30 минут статус «Issued». Затем в бакете `dvorami.ru` → «Безопасность» → «HTTPS» → «Настроить» → источник «Certificate Manager» → сертификат `dvorami`; то же в бакете `www.dvorami.ru`. Так же `sledami.ru`, `www.sledami.ru` и `zalami.ru`, `www.zalami.ru` — своими сертификатами.
И сборка: https://github.com/jastiss/dvorami → **Add file** → **Create new file** → имя `.github/workflows/deploy-yc.yml` → вставить содержимое [docs/deploy-yc.workflow.yml](https://github.com/jastiss/dvorami/blob/main/docs/deploy-yc.workflow.yml) → **Commit changes**.

**Шаг 8. Боты (позже, 5 мин).** Когда мы подготовим функции, пришлём короткую инструкцию: создать секрет в Lockbox и вставить туда токены ботов. Токены не проходят через чат.

**Шаг 9. Закрыть репозиторий (1 мин) — последним.** Только когда мы напишем «боты в облаке, сайты открываются»: https://github.com/jastiss/dvorami/settings → внизу «Danger Zone» → **Change visibility** → **Make private**.

**Что делаем мы после ваших шагов:** выкладываем стенд и проверяем его (шаг 5) → записи зон готовы (шаг 6, 28.11) → после переключения DNS и сертификата выкладываем боевые сайты и проверяем все домены (с www и .рф) с телефона; zalami.ru — когда будет готова витрина `site/zalami/`, до того бакет пуст → переносим ботов в функции и проверяем их на открытом репозитории → вы закрываете репозиторий → отключаем `pages.yml` и старые workflow ботов → обновляем стандарты команды (стенд, ссылки в отчётах, `site-check`).

## 7. Порядок без простоя и если что-то пойдёт не так

1. Пока репозиторий открыт, всё старое работает: стенд на GitHub Pages, боты в Actions. Новое строим рядом.
2. Записи зоны переносим один к одному **до** смены DNS-серверов: почта и проверки поисковиков не теряются ни на минуту. Если dvorami.ru уже показывает сайт с GitHub, на время переключения записи сайта в новой зоне смотрят туда же, на бакет переводим после сертификата.
3. Боты переходят на вебхук по одному; старый workflow отключаем, только когда новый ответил.
4. Репозиторий закрываем последним — после этого GitHub Pages выключится, но он уже не нужен.

| Что случилось | Что будет | Что делаем |
|---|---|---|
| Сборка красная | сайт остаётся прежним | команда чинит, в отчёте строкой |
| Сертификат не выпустился | сайт по HTTPS не открывается, по HTTP открывается | проверяем запись в DNS; до выпуска старая запись ведёт на прежний сайт |
| После смены DNS не приходит почта | — | сравниваем записи MX с reg.ru; можно вернуть DNS-серверы reg.ru за 1 минуту, всё откатится за час-сутки |
| Боевой сайт сломан выкладкой | — | откат из раздела 5, минута |
| Ключ робота утёк | могут подменить файлы в четырёх бакетах (больше ничего) | удаляете ключ в консоли, создаёте новый, меняете секреты — 3 минуты |
| Telegram недоступен из облака | боты не отвечают | 🔶 риск небольшой (на Yandex Cloud много Telegram-ботов); запасной вариант — отдельный маленький сервер, вопрос вам |
| Счёт растёт | письмо от бюджета | смотрим, что тратит; почти всё бесплатно до больших объёмов |

## 8. Что поменяется для вас и для тестеров

- Ссылки на стенд в отчётах станут другими (секретный адрес вместо jastiss.github.io/dvorami). Ссылки на файлы в отчётах продолжат открываться у вас, но не у тех, у кого нет доступа к закрытому репозиторию.
- У тестера, проходившего дело на старом стенде, прогресс и введённый код на новом адресе не сохранятся (браузер хранит их отдельно для каждого сайта). Коды остаются те же.
- Индексация поисковиками остаётся закрытой (решение A-6) и на боевом сайте, пока вы не скажете открыть: в сборке это одна переменная `OPEN_INDEXING`.
