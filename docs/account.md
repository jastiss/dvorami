# Личный кабинет «Мои дела»: архитектура (ADR) и спецификация

Инженер (Opus), 28.11.2026. Заменяет версию 27.11 (кабинет из браузера без сервера).

**Указание владельца 28.11:** «Личный кабинет — это не то, что я представлял. „Список хранится в этом браузере: на другом телефоне его не будет.“ — так не пойдёт. Нужен нормальный современный личный кабинет с виджетами, навигацией, куда можно зайти по логину/паролю (продумать, как они выдаются и валидируются). То есть полноценная разработка со всей архитектурой.» Раньше (27.11): «Личный кабинет должен быть единым… логин/пароль один и внутри могут быть все дела».

Связанные документы: путь покупки и таблицы заказов — `docs/purchase-flow.md`; коды и шифрование дел — `docs/codes.md`; оплата и 152-ФЗ — `docs/payments.md`, `docs/legal/checklist.md`; облако — `docs/yandex-cloud.md`, `platform/ARCHITECTURE.md`; безопасность — `team/std/security.md`.

Значки: 🔶 — цена или лимит по знаниям команды и заголовкам найденных страниц (страницы тарифов мы не открываем), сверить по ссылке перед включением; ⚖️ — вопрос юристу (A-26).

## Коротко

1. **Вход — почта и пароль.** Логин — почта (она нужна и для чека, и для восстановления; отдельное «имя пользователя» — лишнее поле и лишний способ перебора). Пароль задаёт сам человек: после покупки — по ссылке из письма с кодом, без покупки — при регистрации с подтверждением почты кодом. Пароли не придумываем и в письмах не присылаем. Хранение — **argon2id**.
2. **Кабинет — приложение с навигацией и виджетами:** «Обзор» (продолжить дело, сводка, достижения, подарок, «есть код?», заметки, следующее дело), «Мои дела», «Покупки и подарки», «Достижения», «Заметки», «Настройки», «Выйти». На телефоне — нижняя панель, на компьютере — колонка слева.
3. **Один аккаунт на «Дворами», «Следами» и «Залами»;** оформление — марки сайта, с которого вошли.
4. **Прогресс общий между телефонами и людьми одной компании:** хранится по коду дела на сервере, телефон держит копию и играет без сети. При первом входе дела с этого телефона переносятся в аккаунт (с вопросом).
5. **Сервер — Yandex Cloud, Россия:** API Gateway → Cloud Functions (Python) → **YDB serverless**; письма — Postbox; секреты — Lockbox. При наших объёмах — **0–50 ₽ в месяц** сверх уже подключённого 🔶. Managed PostgreSQL отвергнут: от ~1,5–3 тыс. ₽ в месяц за постоянно включённый хост 🔶.
6. **На стенде сейчас — прототип на заглушке API** (`site/account/`): вход, регистрация, восстановление, кабинет со всеми разделами. Помечен «Демо»: принимает только адреса `@example.com`, ничего не отправляет, данные живут в этой вкладке. Код фронта говорит с сервером через один модуль `site/account/api.js` — подключение настоящего API = смена одной строки `<meta name="dv-api">`.
7. **От владельца** — 40–60 минут в консоли YC (раздел 12) и ответ на вопрос о минимальной длине пароля (раздел 13).

## 1. Решения (ADR)

### ADR-1. Логин — почта, пароль — от человека; коды из письма — только для подтверждения и восстановления
- **Контекст.** Владелец просит вход по логину и паролю (28.11). Версия 27.11 предлагала вход без пароля (ссылка и код в письме) — владелец её не принял.
- **Решение.** Логин — почта. Пароль ≥ 10 знаков, любые символы и пробелы, без требований «цифра + заглавная» (раздел 3). Подтверждение почты и сброс пароля — шестизначный код или ссылка в письме. Telegram — второй способ входа на этапе 6.
- **Почему не отдельное имя пользователя:** почту человек и так оставляет при покупке; без почты нельзя восстановить пароль; имя пользователя — ещё одно поле на телефоне и ещё один способ проверить, есть ли человек в базе.
- **Последствия.** Храним хеши паролей (argon2id) — нужны ограничения попыток и письмо о входе с нового устройства. Покупка без аккаунта остаётся: код открывает дело и без входа.

### ADR-2. Бэкенд: Cloud Functions + API Gateway + YDB serverless
| | **YDB serverless** | Managed PostgreSQL |
|---|---|---|
| Цена при нас (≤ 10 тыс. запросов в месяц) | 0 ₽: бесплатно 1 млн единиц запросов (RU) и 1 ГБ в месяц, дальше — порядка 10–20 ₽ за миллион RU 🔶 ([тарифы](https://yandex.cloud/ru/docs/ydb/pricing/serverless), [бесплатный объём](https://cloud.yandex.com/docs/billing/concepts/serverless-free-tier)) | от ~1,5–3 тыс. ₽ в месяц за один самый маленький хост, который включён круглосуточно; отказоустойчивость — ×2–3 🔶 ([тарифы](https://yandex.cloud/ru/docs/managed-postgresql/pricing)) |
| Обслуживание | нет: ни версий, ни дисков, ни окон обновления | версии, обновления, место на диске, подключения из функций через пул |
| Сон без запросов | да, платим только за запросы | нет |
| TTL (автоудаление строк) | встроен: сессии, коды входа, счётчики попыток удаляются сами | задание по расписанию |
| Минусы | свой диалект SQL (YQL), нет внешних ключей, связи держит код; первый запрос после простоя — до ~1 с | — |
- **Решение — YDB serverless.** Связи и уникальность почты держим кодом и первичными ключами (раздел 6). Переезд на PostgreSQL, если когда-нибудь понадобится, — выгрузка таблиц и замена одного модуля доступа к данным.
- **Функции, а не Serverless Containers:** одна функция `account-api` (Python 3.12, 256 МБ) с маршрутизатором внутри — меньше холодных стартов, один деплой; контейнеры нужны, когда появится то, что не помещается в функцию.
- **Почта** — Yandex Cloud Postbox (письма с домена `dvorami.ru`, подпись DKIM — запись в Cloud DNS). **Секреты** — Lockbox. **Капча** — SmartCaptcha, только при подозрительных попытках (этап 6).

### ADR-3. Сессии — непрозрачный токен в cookie HttpOnly, а не JWT
- Токен — 32 случайных байта; в cookie `__Host-dvs` на домене API (`api.dvorami.ru`), в базе — только его SHA-256. `HttpOnly; Secure; SameSite=Lax; Path=/`. Скрипты страницы токена не видят — XSS не может его унести.
- **Почему не JWT:** «Выйти на всех устройствах», смена пароля и удаление аккаунта должны работать сразу; JWT до истечения не отзывается без той же таблицы сессий.
- Срок: 30 дней без входа, не дольше 180 дней всего; каждые сутки активности продлевают. Смена пароля и почты, удаление аккаунта — с вводом текущего пароля.
- `dvorami.ru` и `api.dvorami.ru` — один сайт для браузера (same-site): cookie идёт с запросами страницы, это не сторонняя cookie.
- **Риск — Safari** 🔶: cookie, которую ставит поддомен с IP-адресом из другой сети, чем у основного сайта, Safari ограничивает 7 днями (защита от маскировки трекеров). Бакет сайта и API Gateway — разные адреса Yandex Cloud. Если на этапе 2 тест на iPhone это покажет, API переезжает на тот же адрес: `dvorami.ru/api/…` через API Gateway или CDN перед бакетом; до того в Safari вход раз в неделю.

### ADR-4. Прогресс — по коду дела, телефон играет без сети, при расхождении побеждает тот, кто дальше
- Прогресс принадлежит коду (одна компания — один код — до 6 телефонов, `purchase-flow.md`), а не аккаунту: так у всей компании одна точка. Аккаунт видит прогресс всех своих кодов.
- Плеер по-прежнему пишет всё в `localStorage` после каждого действия и не ждёт сервер. Модуль синхронизации отправляет состояние, когда есть сеть (этап 5). Конфликт: дальше по делу (финал > точка > шаг) — побеждает; журнал событий и заметки объединяются.

### ADR-5. Три домена — один вход через одноразовый билет
- У каждой марки свой API-адрес: `api.dvorami.ru`, `api.sledami.ru`, `api.zalami.ru` — один и тот же API Gateway. Cookie у каждого своя (cookie другого сайта браузеры режут).
- Вошли на «Дворами», открыли «Мои дела» на «Следами» → нет сессии → страница уходит на `api.dvorami.ru/v1/auth/sso?to=sledami` → там сессия есть → обратно с одноразовым билетом (60 секунд, одно использование) → `api.sledami.ru` ставит свою cookie. Без сторонних cookie.

### ADR-6. Фронт — статическая страница и один модуль обмена `api.js`
- Кабинет — статическая страница в бакете, как весь сайт; разделы — `#overview`, `#cases`… без перезагрузки.
- Вся сеть — в `site/account/api.js`: режим `mock` (стенд) или адрес API (боевой). Остальной код кабинета (`app.js`) сети не знает.
- `/account/` — `noindex, nofollow`, нет в sitemap, `Disallow` в `robots.txt` боевого.

## 2. Как появляются логин и пароль

| Путь | Кто | Что происходит | Почта подтверждена |
|---|---|---|---|
| **1. После покупки на сайте** (основной) | покупатель | Оплата прошла → функция находит аккаунт по почте заказа или создаёт приглашение (`status=invited`), привязывает код (роль `buyer`) → письмо: код, «Начать дело» и **«Задать пароль для «Моих дел»** — одноразовая ссылка на 72 часа. Перешёл, придумал пароль, отметил согласие → вошёл. Ссылка истекла — «Забыли пароль?» на ту же почту | переходом по ссылке |
| **1а. Повторная покупка** | у кого аккаунт уже есть | Код сам добавляется в аккаунт с той же почтой; в письме — «Дело уже в «Моих делах»» и «Войти» | уже была |
| **2. Код из подарка, от Tripster или от друга** | получатель | «Создать аккаунт» с полем «Код дела» или «Есть код?» в кабинете. Один код — до 6 аккаунтов (как 6 телефонов). Подарочный код: первый аккаунт — `gift_receiver`, даритель видит «Подарок открыт» | кодом из письма |
| **3. Без покупки** | кто угодно | Почта + пароль + согласие → письмо с шестизначным кодом (15 минут) → аккаунт. Неподтверждённые удаляются через 7 дней | кодом из письма |
| **4. Telegram** (этап 6) | у кого есть Telegram | В настройках «Привязать Telegram» → `t.me/<бот>?start=link_<билет>` → потом вход «через Telegram»: бот спрашивает «Войти на сайт?» | — |

**Почему не выдаём пароль сами:** пароль в письме читает любой, у кого доступ к почте или к пересланному письму, и его никто не меняет. Ссылка «Задать пароль» одноразовая и короткая.

**«Спасибо» после оплаты сессию не выдаёт:** почта в заказе не подтверждена — иначе можно ввести чужую почту и попасть в чужой кабинет. Вход — из письма.

**Восстановление.** «Забыли пароль?» → почта → «Если аккаунт есть, письмо уже в пути» (ответ одинаковый для всех) → в письме ссылка и код, 15 минут, одно использование → новый пароль → все остальные сессии закрыты, на почту — «Пароль изменён. Не вы? Ответьте на письмо». Нет доступа к почте → бот «Вопрос команде»: владелец сверяет заказ (дата, сумма, последние 4 знака кода) и меняет почту командой бота; запись в журнале.

**Смена почты:** текущий пароль → код на новую почту → на старую — письмо «Почта изменена» со ссылкой «Это не я» (24 часа вернуть). **Удаление:** текущий пароль → сразу удаляются аккаунт, сессии, заметки, привязки; заказы обезличиваются (раздел 9).

## 3. Проверка логина и пароля

**Почта:** убираем пробелы по краям, NFKC, нижний регистр, домен на кириллице — в punycode; до 254 знаков; простая проверка вида `x@y.z`. Одноразовые почтовые сервисы не запрещаем.

**Пароль** (по NIST SP 800-63B-4 и OWASP; [NIST](https://pages.nist.gov/800-63-4/sp800-63b/authenticators), [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)):
- **не короче 10 знаков**, до 128; любые символы, пробелы, эмодзи; NFKC перед хешированием;
- без правил «цифра, заглавная, спецзнак» и без принудительной смены по сроку — они делают пароли предсказуемее;
- запрет: пароль из списка частых и утёкших (100 тыс. строк — файл в функции, наружу ничего не отправляем), пароль = почта или её часть до «@», один символ подряд;
- можно вставлять из менеджера паролей; на экране — «Показать», подсказка «удобно 3–4 слова через пробел»;
- NIST для пароля как единственного фактора просит 15 знаков; мы берём 10 из-за телефона на улице и компенсируем ограничением попыток и письмом о входе с нового устройства — **вопрос владельцу, раздел 13**.

**Хранение:** argon2id, память 19 МиБ, 2 прохода, 1 поток (минимум OWASP; ~50–100 мс на функцию 256 МБ); строка PHC `$argon2id$v=19$m=19456,t=2,p=1$…` с солью. Параметры выросли — пароль перехешируется при следующем входе. Перед хешированием — HMAC с «перцем» из Lockbox (`pepper_v` в записи — номер версии): утёкшая база без Lockbox не перебирается.

**Ограничения попыток** (счётчики в YDB с TTL; IP не храним — только HMAC от IP с суточной солью):
| Действие | Ограничение | Что видит человек |
|---|---|---|
| Вход | 5 неудач на почту за 15 минут, потом 1 попытка в минуту; 20 неудач с одного IP за 10 минут | «Неверная почта или пароль» → «Слишком много попыток. Подождите 15 минут или восстановите пароль» |
| Код из письма | 5 попыток на код, потом код недействителен | «Код не подошёл» → «Запросите новый код» |
| Письма (регистрация, сброс, повтор) | 3 в час на почту, 10 в час с IP; «Отправить ещё раз» — через 60 с | «Письмо отправлено» |
| Всё API | ограничение запросов в секунду на маршрут в API Gateway 🔶 | «Сервис занят, попробуйте через минуту» |
| Подозрительный всплеск | SmartCaptcha (этап 6) | невидимая проверка |

**Без подсказок для перебора** (`team/std/security.md`, п. 7): на вход — один ответ «Неверная почта или пароль» и для неизвестной почты (с фиктивным хешированием, чтобы время ответа не выдавало); регистрация и сброс всегда отвечают «Письмо отправлено» (если почта занята — письмо «У вас уже есть аккаунт: войдите или восстановите пароль»); ошибки кода — без длины и алфавита сверх напечатанного.

**CSRF:** (1) cookie `SameSite=Lax`; (2) изменения — только `POST/PATCH/DELETE` с телом `application/json` (с чужого сайта это требует предварительного запроса CORS, а его API не разрешит); (3) проверка заголовка `Origin` по списку наших доменов; (4) заголовок `X-CSRF-Token` = HMAC(ключ, id сессии) из ответа `GET /v1/session`. CORS — только наши домены, с `credentials`.

**Прочее:** письмо «Вход с нового устройства: iPhone · Safari, 28 ноября 19:05» (устройство — грубо, без IP и модели); страница кабинета не открывается во фрейме (на боевом — заголовок `frame-ancestors 'none'` через API Gateway или CDN; на стенде — проверка в скрипте); CSP — `<meta>` на странице; в журналах — `user_id`, а не почта.

## 4. API

База — `https://api.<домен марки>/v1`. Тело и ответ — JSON. Ошибка — `{"error": "<код>", "retry_after": N?, "field": "…"?}`; коды: `bad_credentials`, `rate_limited`, `weak_password`, `bad_email`, `bad_code`, `expired`, `consent_required`, `unauthorized`, `csrf`, `server`. Методы `api.js` — в скобках.

| Метод | Что | Ответ |
|---|---|---|
| `GET /session` (`session`) | есть ли вход | `{user \| null, csrf}` |
| `POST /auth/login` {email, password} (`login`) | вход | `{user}` + cookie |
| `POST /auth/logout`, `/auth/logout-all` (`logout`, `logoutAll`) | выход здесь / везде | 204 |
| `POST /auth/register` {email, password, consent, code?} (`register`) | регистрация | 202 `{next: "verify"}` — всегда |
| `POST /auth/verify` {email, code} (`verify`) | код из письма | `{user}` + cookie |
| `POST /auth/resend` {email, purpose} (`resend`) | письмо ещё раз | 202 |
| `POST /auth/forgot` {email} (`forgot`) | восстановление | 202 — всегда |
| `POST /auth/reset` {email, code \| token, password} (`reset`) | новый пароль | `{user}` + cookie, остальные сессии закрыты |
| `GET /auth/set-password?token=…` (`inviteInfo`) | чья ссылка «Задать пароль» (почту показать, не спрашивать) | `{email, quest}` / `expired` |
| `POST /auth/set-password` {token, password, consent} (`setPassword`) | первый пароль после покупки | `{user}` + cookie |
| `GET /auth/sso?to=…`, `GET /auth/sso/finish?ticket=…` | вход на другой марке | редирект |
| `GET /me/dashboard` (`dashboard`) | всё для «Обзора»: дела со сводкой прогресса, достижения, последняя заметка, покупки | см. раздел 7 |
| `POST /me/codes` {code} (`addCode`) | добавить код | `{case}` / `bad_code` |
| `POST /me/import` {items:[{quest, code?, state, rating?}]} (`importLocal`) | перенос дел с телефона | `{added, merged, skipped}` |
| `GET /progress/{quest}?code=…`, `PUT /progress/{quest}` {code, rev, state} | прогресс дела (плеер) | `{rev, state}` — уже объединённый |
| `GET /me/orders` (`orders`) | покупки и подарки | список |
| `POST /me/orders/{id}/resend`, `/refund` (`giftResend`, `refund`) | подарок: отправить ещё раз / вернуть деньги, пока код не открыт | 202 |
| `GET /me/achievements` (`achievements`) | достижения | список |
| `GET/POST /me/notes`, `PATCH/DELETE /me/notes/{id}` (`notes`, `addNote`, `editNote`, `deleteNote`) | заметки | список / заметка |
| `GET/PATCH /me/settings` (`settings`, `saveSettings`) | «Следами» в «Дворами», рассылка | настройки |
| `POST /me/password` {current, password} (`changePassword`) | смена пароля | 204, остальные сессии закрыты |
| `POST /me/email` {email, password} → `POST /me/email/verify` {code} (`changeEmail`, `verifyEmail`) | смена почты | 202 / `{user}` |
| `GET /me/sessions`, `DELETE /me/sessions/{id}` (`sessions`, `endSession`) | устройства | список / 204 |
| `GET /me/export` (`exportData`) | мои данные (ст. 14 152-ФЗ) | JSON |
| `DELETE /me` {password} (`deleteAccount`) | удалить аккаунт | 204 |

Плеер без аккаунта тоже синхронизируется по коду (`device_id`, `purchase-flow.md`) — эндпоинт `progress` один.

## 5. Перенос дел с телефона при первом входе

1. После входа `app.js` читает сохранения плеера на этом телефоне: `dvorami:play:<id>` (прогресс, журнал, заметки — события `note`), `dvorami:code:<id>` (код), `dvorami:rating:<id>` (оценка).
2. Есть дела, которых нет в аккаунте, — вопрос: «На этом телефоне 2 дела: Синяя птица (точка 5), Туман в овраге (раскрыто). Добавить их в аккаунт?» [Добавить] [Не сейчас]. Спрашиваем, потому что телефон может быть общим (семья, друг дал поиграть).
3. `POST /me/import`: для каждого дела с действующим кодом — привязка кода (роль `member`, если код не его), объединение прогресса (раздел 8), заметки из журнала — в заметки аккаунта, оценка — если её ещё нет. Дело без кода (стенд, мастер-код) — `skipped`: на экране «осталось на этом телефоне».
4. Телефон помнит `dvorami:acct:imported:<user_id>` — вопрос не повторяется; новое дело на этом телефоне — вопрос снова.
5. Локальные сохранения не удаляются: это офлайн-копия плеера.

Коды тестеров стенда сейчас живут без сервера (`docs/codes.md`, запечатанные записи); при запуске сервера команда переносит их в таблицу `codes` из `.codes/` (не из репозитория).

## 8. Синхронизация прогресса

- Телефон: каждое действие → `localStorage` (как сейчас) → очередь отправки; есть сеть и код — `PUT /progress/{quest}` с последним известным `rev`.
- Сервер: `rev` совпал — принять, `rev+1`. Не совпал — объединить: «дальше» = больше (номер точки, фаза: walk < step < point_done, шаг); финал важнее всего; журналы — объединение по (время, тип, точка), не больше 500 событий; заметки — объединение по id. Ответ — объединённое состояние; телефон берёт его, если оно дальше своего (`purchase-flow.md`: «засчитывается тот, кто дальше»).
- Другой телефон компании видит точку при следующем открытии дела или кабинета (опрос раз в 30 с только на экране «ждём остальных» — этап 5; без постоянного соединения — батарея).
- Версия сценария другая — сервер не смешивает разные версии, плеер спрашивает «доиграть или начать заново» (H-74).

## 9. Персональные данные (152-ФЗ)

Не юридическая консультация; ⚖️ — юристу (A-26).
- **Что храним:** почта, Telegram id (если привяжут), тексты заметок, хеш пароля, грубое имя устройства. Ни имени, ни телефона, ни даты рождения, ни IP (только HMAC от IP на сутки для ограничения попыток).
- **Где:** YDB и функции — Yandex Cloud, регион ru-central1, Россия (ч. 5 ст. 18 152-ФЗ). Зарубежных сервисов в цепочке нет: список утёкших паролей — файл в функции, а не запрос наружу.
- **Согласие** — отдельным документом (`/legal/consent/`, с 1.09.2025): галочка, не проставленная заранее, при регистрации и при «Задать пароль»; версия согласия и время — в `users`. Рассылка — отдельное согласие, по умолчанию выключено. ⚖️ — нужна ли галочка, если аккаунт — часть исполнения договора (п. 5 ч. 1 ст. 6).
- **Политика** (`docs/legal/privacy.md`) — дописать раздел «Аккаунт»: какие данные, зачем, сроки, как удалить; уведомление в Роскомнадзор — дополнить целью «личный кабинет» (`payments.md`).
- **Сроки:** коды входа — 15 минут; сессии — 30 дней без входа (не больше 180); неподтверждённый аккаунт — 7 дней; аккаунт без входа 3 года — письмо и удаление через 30 дней; прогресс — 90 дней после `play_until`; журнал входов — 1 год; заказы — по налоговым срокам, отдельно.
- **Права человека:** «Скачать мои данные» — JSON (ст. 14); «Удалить аккаунт» — сразу аккаунт, сессии, заметки, привязки, оценки; заказы обезличиваются (почта → хеш) до конца налогового срока (ст. 9, отзыв согласия).
- **Метрика на странице кабинета:** Вебвизор на `/account/` выключен (`analytics.js`, `WEBVISOR_SKIP`, как в плеере); на всякий случай поля почты и пароля — `ym-disable-keys`, содержимое кабинета — `ym-hide-content`; в параметрах целей — только раздел, состояние, число дел; почта в Метрику не уходит никогда.
- **Защита** (ст. 19): доступ к базе — только у сервисного аккаунта функции; секреты — в Lockbox; резервные копии YDB — в том же облаке. ⚖️ — уровень защищённости и модель угроз для ИСПДн.

## 14. Перелинковка линий и порядок блоков витрины

- **Полоса линий над шапкой** на всех витринах трёх марок: «Дворами · Следами 18+ · Залами скоро — Мои дела»; текущая линия выделена; нейтральный тёмный фон — полка платформы, а не часть марки. На телефоне уже 440 px «Залами» — в подвале. Плеер — без полосы.
- **«Другие линии» в подвале** главной, каталога, страниц дел и «Следами»; «Мои дела» — в ссылках подвала каждой витрины.
- **Блок «Другие линии» в теле страницы** (`section#other`, главная «Дворами» и «Следами»): карточка каждой другой линии — «Следами» (18+, без сюжетов), «Дворами», «Залами» (музейная линия, отдельный сайт zalami.ru по A-77; пока витрины нет — «скоро», ссылка только на канал, где объявим запуск). Собирается `scripts/build_cases.py` (`other_html` из `LINES`, метки `<!-- other:start -->` / `<!-- other:end -->`), руками не правится: новая линия появляется во всех блоках разом. Появится витрина «Залами» — в `LINES` ставится `url`.
- **Порядок блоков** (владелец 28.11: «эти блоки должны быть выше блоков под SEO/GEO»): блок «Другие линии» — выше справочных SEO/GEO-блоков (`<!-- seo:start -->`) и FAQ. Общее правило для всех витрин: блоки для посетителя (дела, как это устроено, для кого, другие линии, отзывы) — выше SEO/GEO-справки и FAQ, они в конце страницы перед контактами. `site_check --sync` (`otherIssues`, самопроверка `otherSelftest`) краснеет, если блок ниже `seo:start` или `#faq`, если в нём нет какой-то линии из `LINES` или у линии без витрины есть ссылка на витрину.
- **Ссылки несут откуда и город:** `?from=<марка>` и `data-city-href`; клики — цель `brand_cross` (`place`: lines / footer / block), «Мои дела» — `account_open`.

## 15. Метрики

Цели (без персональных данных — только раздел, состояние, число дел, способ): `account_open`, `account_view {brand, items}`, `account_nav {view}`, `account_continue {quest, state}`, `account_code`, `account_next`, `login_start`, `login_ok {how: password|code|set|tg}`, `login_fail {why}`, `signup_start`, `signup_ok`, `reset_start`, `reset_ok`, `import_ok {added}`, `note_add`.

| Что меряем | Зачем | Порог для разбора |
|---|---|---|
| Начатые дела, к которым вернулись после паузы | кабинет возвращает к делу | < 60% |

| `login_ok / login_start`; доля «забыли пароль» | форма понятна, пароли не теряют | < 80%; > 15% |
| Перенос с телефона: «Добавить» / показан вопрос | вопрос понятен | < 60% |
| Продолжили на другом телефоне | нужен ли общий прогресс | динамика |
| Раскрыто / начато | доходят ли до финала | < 70% |
| «Выбрать следующее дело» → оплата за 90 дней | кабинет как канал продаж | < 10% |
